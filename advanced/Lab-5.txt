## 2. Lab 5A – Erfolgreiche Übertragung nachweisen

Eine robuste Anwendung unterscheidet mindestens vier Ergebnisse:

1. Das Kommando wurde vom Host abgesendet.
2. Das Modem hat das Kommando akzeptiert.
3. Der Transport hat eine Antwort vom Cloud-Endpunkt erhalten.
4. Die Anwendung hat eine fachliche Bestätigung erhalten, falls diese erforderlich ist.

`OK` ist nicht gleich „Nachricht in der Cloud angekommen“. Beim nRF93M1 melden `%COAP:`-URCs den Fortschritt und das Ergebnis einer CoAP-Transaktion. Eine erfolgreiche CoAP-Antwort – beispielsweise `2.01 Created` – ist ein stärkerer Nachweis als die bloße Annahme des AT-Kommandos. Sie beweist allerdings nicht automatisch, dass nachgelagerte Cloud-Verarbeitung oder ein Datenbank-Write abgeschlossen ist.&#x20;

### Aufgabe: Nachricht senden und Status protokollieren

Im AT-Modell:

```
AT+CEREG?
AT%NRFCLOUDMESSAGE
```

Die zweite Zeile ist hier nur ein Platzhalter für den Sendeaufruf. Verwendet die genaue Payload-Syntax aus dem AT Command Reference Guide der installierten Modem-Firmware. Eine mögliche Nachricht ist:

```
{
  "appId": "ADVANCED_WORKSHOP",
  "data": {
    "messageId": "device-01-000042",
    "sequence": 42,
    "temperature": 21.7
  }
}
```

Beobachtet und protokolliert:

- Zeit des Sendeversuchs;
- eindeutige Nachrichten-ID und Sequenznummer;
- sofortige AT-Antwort;
- alle zugehörigen `%COAP:`-URCs;
- finales Ergebnis und Dauer;
- optional den Eingang der Nachricht in nRF Cloud.

Wichtig: `%COAP:`-URCs können während anderer Cloud-Transaktionen eintreffen. Korreliert sie daher über den Transaktionszustand und die Ereignisfolge, statt jede URC blind der zuletzt gesendeten Nachricht zuzuordnen.&#x20;

## 3. Lab 5B – Retry-Strategie ohne Datenchaos

Der kniffligste Fall ist ein unklares Übertragungsergebnis: Der Host wartet auf eine Bestätigung, aber die Verbindung bricht ab. Wurde die Nachricht übertragen? Ist die Bestätigung verloren gegangen? Ein erneuter Versand kann dann zu Duplikaten führen.

Eine robuste Strategie verwendet eine eindeutige `messageId` und behandelt Wiederholungen ausdrücklich.

Nachricht in Outbox speichern

ID, Sequenznummer, Payload, Zeitstempel

Senden und Ergebnis abwarten

Bestätigt

Nachricht als abgeschlossen markieren.

Unklar / Fehler

Status prüfen, Backoff anwenden, ggf. mit derselben ID wiederholen.

### Aufgaben

1. Erzeuge für jede neue Messung eine eindeutige Nachrichten-ID.
2. Speichere ausstehende Nachrichten, wenn sie einen Neustart überleben müssen.
3. Wiederhole bei vorübergehenden Netzwerkfehlern mit begrenztem Backoff.
4. Verwende bei einer Wiederholung dieselbe ID für dieselbe logische Nachricht.
5. Sorge auf der Empfängerseite für Deduplizierung, wenn Mehrfachverarbeitung unzulässig ist.

Eine Nachrichten-ID allein verhindert keine Duplikate. Der Empfänger muss sie erkennen und bereits verarbeitete Nachrichten entsprechend behandeln. Auch ein Transport-ACK und eine fachliche Anwendungsbestätigung sind unterschiedliche Dinge.

## 4. Lab 5C – TLS/DTLS und Credentials

Beim nRF93M1 stehen TLS 1.2, TLS 1.3 und DTLS 1.2 zur Verfügung. nRF Cloud verwendet für den integrierten CoAP-Client DTLS 1.2. Das Modem bietet außerdem TLS-Kontexte und eine Dateisystem-Schnittstelle für Zertifikate und Schlüssel.&#x20;

| Sicherheitsfrage                  | AT-Modell mit nRF Cloud                                                             | PPP mit Cloud-Client auf Host                                                   |
| --------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Wo endet die DTLS-Sitzung?        | Im Modem                                                                            | Im Host                                                                         |
| Wer verwaltet Cloud-Credentials?  | Modem-Cloud-Client und Provisionierungsprozess                                      | Host-Anwendung / Cloud-Bibliothek                                               |
| Wo liegen Host-seitige Schlüssel? | Cloud-Schlüsselverwaltung im Modem; Host muss eigene Geheimnisse weiterhin schützen | Im geschützten Speicher des Hosts                                               |
| Was muss getestet werden?         | Provisionierung, Gerätezeit, Cloud-URCs, DTLS-Status                                | Zertifikate, Trust Store, Systemzeit, TLS-/DTLS-Konfiguration und PPP-Datenpfad |

### Sicherheitsaufgabe

Diskutiert im Team folgende Fälle:

- Ungültige Systemzeit: Ein JWT oder die Zertifikatsprüfung kann fehlschlagen. Vor einer Änderung der Credentials die Zeitbasis prüfen.
- Zertifikat abgelaufen oder falsche CA: TLS-Fehlerursache erfassen, nicht die Serverauthentifizierung abschalten.
- Schlüssel im Klartext geloggt: Logs bereinigen und die sichere Speicherung bzw. Provisionierung korrigieren.
- DTLS-Timeout: Netzwerk-, Zeit- und Sitzungszustand untersuchen, bevor die Anwendung Credentials neu provisioniert.

Die Gerätezeit ist für die nRF-Cloud-Authentifizierung relevant; Nordic dokumentiert außerdem die Speicherung von Zertifikaten, privaten Schlüsseln und Root-CAs im Modem-Dateisystem.&#x20;

## 6. Abnahmekriterien

- Eine Nachricht wird mit eindeutiger ID übertragen und ihr Transportergebnis protokolliert.
- Die Anwendung unterscheidet Kommandoannahme, CoAP-Ergebnis und fachliche Bestätigung.
- Temporäre Fehler führen zu begrenzten Wiederholungen mit Backoff.
- Wiederholungen erzeugen keine unkontrollierten Duplikate.
- TLS-/DTLS-Fehler werden diagnostiziert, ohne Sicherheitsprüfungen abzuschalten.
- Geheimnisse tauchen nicht in Logs oder im Quellcode auf.
